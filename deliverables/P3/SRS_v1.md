# 第三阶段需求分析与概要设计（v1）

## 1. 系统定位

本阶段将 CompKey 算法从“单次实验脚本”升级为“可维护、可追踪、可评估的推荐系统骨架”。系统强调离线计算与在线查询分离，避免用户每次检索都重新跑完整算法。

## 2. 角色与使用场景

### 2.1 角色

- **业务使用者**：输入种子关键词，查看竞争性关键词推荐结果。
- **系统维护者**：创建数据库、导入离线结果、查看日志与反馈。
- **算法维护者**：调整权重、更新候选词、重新生成推荐结果。

### 2.2 典型场景

1. 用户输入“口红”，系统返回若干竞争性候选词。
2. 系统先从数据库读取已有推荐结果，再按排序输出。
3. 用户提交反馈，系统将反馈写回数据库，供后续优化使用。

## 3. 功能需求

### 3.1 必需功能

- 创建并初始化数据库表。
- 导入关键词、中介关键词、推荐结果、搜索记录与用户反馈。
- 根据种子词查询推荐结果。
- 记录查询日志与反馈日志。
- 支持结果更新与重建。

### 3.2 过程性要求

- 离线阶段完成分词统计、候选词聚合、竞争度计算。
- 在线阶段只做查询、排序输出、日志写入。
- 对空输入、无结果、数据库异常进行统一处理。

## 4. 非功能需求

### 4.1 模块化

系统至少分为：数据层、处理层、算法层、服务层、展示层。

### 4.2 可维护性

- 数据访问与业务逻辑分离。
- 算法参数集中配置。
- 结果表具有明确主键、唯一约束和索引。

### 4.3 性能目标

本阶段性能目标不是追求极限，而是建立可量化口径：

| 指标 | 目标口径 |
| --- | --- |
| 数据库初始化 | 一次性建表和索引，结果可复现 |
| 离线导入 | 批量写入优先，避免逐条提交 |
| 在线查询 | 常规 seed 查询应保持毫秒级到百毫秒级 |
| 热点推荐 | 缓存命中后显著低于冷查询 |

### 4.4 稳定性

- 支持重复初始化，不因重复运行而破坏数据结构。
- 支持“无结果时返回空列表”而非报错退出。

## 5. 验收口径

- 能完成表创建、插入、查询、更新四类操作。
- 能从输入关键词到推荐结果输出形成完整链路。
- 能给出至少 3 个性能指标：初始化耗时、查询耗时、推荐耗时。
