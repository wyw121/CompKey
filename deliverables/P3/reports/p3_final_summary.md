## 详细说明（数据来源与第三阶段处理）

1) 数据来源
- 原始搜索日志：`数据分析与商务智能数据/数据/user_tag_query.10W.TRAIN`（共 100000 行）。
- P1 输出（用于 P3）：
	- `deliverables/P1/run_train_v2_full/cleaned_queries_v1.csv`（清洗后查询）
	- `deliverables/P1/run_train_v2_full/tokenized_queries_v1.csv`（分词结果，token_count=1207）
	- `deliverables/P1/run_train_v2_full/word_freq_v1.csv`（全局词频）
	- `deliverables/P1/run_train_v2_full/seed_related_queries_v1.csv`（与种子相关的查询，seed_related_count=265）
	- `deliverables/P1/seed_keywords_v1.csv`（种子表）

2) 离线处理（位置与实现）
- 代码位置：`deliverables/P3/compkey_p3/offline_pipeline.py`。
- 核心流程：
	1. 从 `seed_keywords_v1.csv` 读取种子（`load_seed_keywords`）。
	2. 从 `word_freq_v1.csv` 读取全局频率（`load_global_frequency`）。
	3. 读取 `tokenized_queries_v1.csv`，统计每个 seed 与 token 的支持度与出现的独立 (user,query) 对（用于 query_count）。
	4. 为每个 seed 计算中介关键词（mediator）与权重：
		 - local_share = support_count / total_tokens_for_seed
		 - rarity = 1 / (1 + log1p(global_frequency))
		 - weight = round(local_share * rarity, 6)
	5. 构建候选竞争度（competition_score）：
		 - score = round(weight * (1 + log1p(support_count)) * (1 / (1 + log1p(global_frequency))), 6)
	6. 将 `keyword` / `intermediary_keyword` / `competition_result` / `search_log` 批量 upsert 写入 SQLite（通过 `CompKeyRepository`）。

3) 在线服务（位置与实现）
- 代码位置：`deliverables/P3/compkey_p3/service.py`（RecommendationService）与 `deliverables/P3/compkey_p3/repository.py`（DB 封装）。
- 推荐流程：
	1. 接收 seed 输入（去空格）。
	2. 检查 LRU 缓存（`RecommendationCache`，默认 size=128）。缓存命中直接返回。
	3. 缓存未命中时调用 `CompKeyRepository.fetch_results_for_seed` 查询 `competition_result` 表（按 competition_score desc 排序，limit N）。
	4. 将结果对象序列化并写入缓存。

4) 数据库与表（schema）
- schema 文件：`deliverables/P3/db_schema_v1.sql`。
- 主要表与索引：
	- `keyword`（keyword, domain, description）
	- `intermediary_keyword`（seed_keyword, mediator_keyword, support_count, query_count, global_frequency, weight），并对 `seed_keyword` 建索引
	- `competition_result`（seed_keyword, candidate_keyword, competition_score, rank_no, evidence_source），并对 `(seed_keyword, competition_score)` 建索引
	- `search_log`（保存样本查询与来源文件）
	- `user_feedback`（用户反馈）

5) 方法与关键公式
- local_share = support_count / total_tokens_for_seed
- rarity = 1 / (1 + log1p(global_frequency))
- weight = local_share * rarity
- competition_score = weight * (1 + log1p(support_count)) * (1 / (1 + log1p(global_frequency)))

6) 横向对比（已做 / 建议）
- 分词：当前使用 `jieba`（在 P1 中加载缓存并分词）。备选：基于规则的正则切分（已作为回退），以及其他中文分词库（HanLP/THULAC）可用于对比。当前小样本下差异不明显；若要衡量对候选词覆盖的影响，建议用同一批数据分别跑 3 种分词器并比对 `token_count`、候选覆盖数与最终 `competition_result` 的 Jaccard/Top-K 重叠。
- 存储：当前用 SQLite（WAL 模式），优点：零运维，便于交付；缺点：并发写入受限。横向对比建议：在中/大规模数据上将 SQLite 与 PostgreSQL/MySQL 比较，可重点测量并发写入吞吐与并发查询延时。

7) 性能评估与模块耗时（本次实测）
- 数据规模（本次构建产物）：seed_count=15, mediator_count=474, competition_count=298, search_log_count=210；P1 输出 token_count=1207, seed_related_count=265。
- 基准（见 `reports/p3_performance_summary.md`）：
	- 数据库初始化耗时：41.648 ms
	- 离线导入耗时：114.985 ms
	- seed 查询平均耗时：0.068 ms
	- 推荐冷启动平均耗时：0.103 ms
	- 推荐缓存命中平均耗时：0.001 ms
	- 端到端总耗时：175.123 ms

	说明与量化：离线导入在本次运行中大约写入 997 行记录（15+474+298+210）。因此观测到的平均写入成本约为：

	- 单行写入成本 ≈ 114.985 ms / 997 ≈ 0.115 ms/row（含事务与索引开销，基于 SQLite + WAL + 批量 executemany）。

	- 以该经验粗略估算：若扩展到 1,000,000 行，线性估计写入时间 ≈ 0.115 ms * 1,000,000 ≈ 115,000 ms ≈ 115 s（仅作能力估算；实际系统吞吐会受 IO、事务批次大小、索引数量影响）。

	- 缓存收益（实测）：从冷启动平均 0.103 ms 降到缓存命中 0.001 ms，约 103x 的平均延迟改善（在当前样本/硬件上）。

8) 优化点与实际带来效果（本次可测的）
- 建索引（seed/candidate）使在线查询稳定，显著降低查询方差（未单独给出对比数值）。
- 使用 WAL 与批量 executemany：在本小规模数据上，离线导入总耗时 114.985 ms，若改为逐条插入预计会明显变慢（因事务/commit 频繁）。
- 缓存（LRU 128）：对热点 seed 带来约 100x 延迟下降（0.103→0.001 ms）。

9) 日志、缓存与度量建议
- 日志：在线每次查询建议写入 `search_log`（已实现插入接口）；对异常和空结果做专门标记，便于离线质量回溯。
- 指标监控：记录每次在线查询的 latency_ms、cache_hit（bool）、result_count、db_query_rows；离线任务记录每阶段耗时（读取、聚合、写入）。
- 缓存策略：当前 LRU(128) 为默认，建议对生产流量做热词采样并按访问频度调整（例如将热点 top 1% 缓存大小扩大），并在缓存失效时异步预热。

10) 扩展与风险
- 并发写入：SQLite 在高并发场景下会成为瓶颈，建议当写入/查询并发上升时迁移到 PostgreSQL，并使用批量 COPY/事务分区。
- 数据漂移：离线构建必须保留原始 P1 输出引用（文件名/时间戳），以便溯源。
